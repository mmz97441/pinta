## Garanties techniques et limites de la preuve

La migration `20260917000001_admin_simplification.sql` ajoute les commandes atomiques tarifs/catégories, les commandes ciblées modèles/règles/abonnement, la suspension protégée et la garde de conservation de l’historique client. Les permissions d’écriture ne sont pas déduites du seul affichage d’un onglet. Chaque mutation réussie est auditée. Les anciennes offres `premium` sont conservées ; les valeurs explicites `premium_mensuel` et `premium_annuel` sont ajoutées au type historique s’il existe, sans reclasser les clients.

Les brouillons sont partitionnés par utilisateur via le hook commun. Les commandes tarif/catégorie/modèle/règle/abonnement vérifient une version attendue. Les coordonnées client continuent d’utiliser le service d’édition existant ; cette livraison ne prétend pas ajouter un verrou inter-utilisateurs à ce formulaire.

Les fixtures navigateur n’attestent pas qu’un serveur de production accepterait un payload invalide. Elles prouvent les requêtes émises ou empêchées par l’interface. Les protections serveur ont été vérifiées séparément dans PostgreSQL jetable, toutes migrations appliquées ; aucune donnée de production n’est utilisée. L’envoi et la livraison effective d’un email d’invitation restent dépendants du fournisseur configuré, sans test d’envoi réel ici. Une erreur de provisionnement après émission de l’invitation supprime le nouveau compte auth ; cet email déjà émis ne peut pas être rappelé.

Preuves actuelles :

- `/tmp/pinta-admin-simplicity-4187-final/results.json` : 10 scénarios navigateur sur build figé, 10 réussites, aucune exception ni requête externe imprévue ; captures associées.
- `/tmp/pinta-admin-permissions-4187/results.json` : 12 scénarios permissions réussis sur build figé.
- `/tmp/pinta-admin-sql-final.log` : 46 assertions réussies, dont quatre de suivi client déléguées à cette exécution et une concurrence réelle à deux sessions. L’erreur `40001` affichée pour la session perdante est attendue et vérifiée par le runner.
- `/tmp/pinta-admin-unit-edge.log` : 15 tests unitaires/import/export/Edge réussis.
- `npm run build` et ESLint ciblé : réussis avant intégration ; recontrôle global et recette finale figée par root.

Déploiement requis, à effectuer par l’intégrateur après validation globale : migration01 avant le frontend, puis redéploiement de `create-staff-user` avec `APP_URL` HTTPS existant. Aucune nouvelle clé secrète ni nouvelle entrée de fonction n’est requise. Le déploiement de la migration doit être validé et commité avant tout usage des nouvelles valeurs enum d’abonnement.

## Contre-revue indépendante des changements root

Lecture de `20260917000002_client_outgoing_tracking.sql` : accès limité aux dossiers demandés appartenant au client authentifié, profil actif requis et statut sorti requis ; seul le suivi principal est retourné. Le manifeste et les autres clients ne sont pas exposés. Les quatre assertions de propriété, profil inactif, refus anonyme et RLS manifeste passent dans le runner SQL ci-dessus.

Lecture de `20260917000003_manual_notification_control.sql`, `relances-auto` et `_shared/telegram.ts` : la migration vise seulement les rappels automatiques non envoyés portant le préfixe `reminder:` ; l’historique envoyé et les envois manuels restent conservés. Le worker ne crée plus de notification client et le dispatch bloque également un ancien rappel avant tout appel fournisseur. L’exécution de l’outbox manuelle et de l’OCR continue. Aucun blocage concret identifié dans cette revue.

Lecture de `telegram-inbox-document` : session équipe et droit Telegram requis, message non affecté requis, chemin Telegram contrôlé, aperçu limité PDF/images et 10 Mo contrôlés pendant la lecture ; token fournisseur jamais transmis au navigateur, réponse sans cache. Aucune écriture métier. Cette contre-revue est une lecture de code ; les tests Edge de root constituent la preuve d’exécution, pas un téléchargement réel de document client.

### Dernière contre-vérification avant publication

Verdict : aucune réserve bloquante identifiée sur les commandes serveur et `pinta/scripts/deployment/simplification20260917.py`. Le script vérifie les empreintes avant répétition/application, exécute la répétition avec `ROLLBACK`, applique et enregistre les trois migrations dans une seule transaction avec timeouts, protège les sauvegardes privées (dossier 0700, fichiers 0600), puis vérifie présence/ACL des commandes et absence de rappels automatiques en attente. Aucun nouvel enum n’est utilisé avant le commit. Simulation locale du script avec le module réseau intégralement remplacé : répétition, application simulée, vérification et refus de réécraser la sauvegarde après application conformes. Cette simulation n’a effectué **aucun appel de production**.

Contrôles supplémentaires exécutés : `/tmp/pinta-admin-security-final.log` contient **50 assertions SQL réussies**, incluant paramètres nuls, profil opérateur inactif, directeur inactif et périmètre de suivi nul (aucun dossier retourné). Les permissions, CAS et droits limités de suivi restent respectés.

`inbox-preview.edge.test.cjs` comporte désormais **5 tests réussis** : le préparateur sans droit Telegram est refusé avant appel fournisseur ; un flux réel de 12 Mio annoncé à 100 octets est interrompu au-delà de 10 Mio, son lecteur est annulé et aucun secret n’apparaît dans la réponse. Le scénario autorisé utilise aussi un préparateur possédant uniquement le droit requis, pour distinguer correctement refus et autorisation.

Ordre d’exploitation recommandé : publier le worker manuel et les fonctions embarquant la garde anti-`reminder:` avant, ou au plus près de, l’application de la migration03. Cela évite qu’une ancienne version du worker recrée un rappel entre son annulation en base et sa mise à jour. La vérification du script couvre l’état de la base ; le contrôle du code effectivement publié des fonctions reste une étape séparée du déploiement.
